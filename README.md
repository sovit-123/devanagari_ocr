# Devanagari OCR Benchmarks

Training and validating different OCR models on Devanagari text.
The goal is a fair, reproducible comparison of models (classical and
vision-language) on a large compiled Devanagari dataset, scored with a
single shared evaluation protocol.

## The dataset

[himalaya-ai/devanagari_ocr_dataset](https://huggingface.co/datasets/himalaya-ai/devanagari_ocr_dataset)
-- a compilation of 7 public Devanagari OCR datasets, ~60 GB total:

- **7,514,225 samples**, each exactly one image with one ground-truth
  transcription (verified: no duplicates, no multi-image records)
- **42 image tarballs** (~1.4 GB each) plus one monolithic annotations
  file, `devanagari_ocr.json` (~2.1 GB)
- Languages: Nepali, Hindi, Marathi, Pali/Sanskrit, mixed Devanagari and
  Latin digits; filename prefixes (`nepali_…`, `hindi_local_…`,
  `hindidataocr_…`) indicate the source dataset and can serve as
  pseudo-domain labels
- No predefined splits -- this project creates its own (seed 42)

**Schema note:** the annotations actually use a chat-style `messages`
schema (user asks for the transcription, assistant reply is the ground
truth, `images` list holds one path like `devanagari_ocr/nepali_0.png`).
The dataset card describes an older ShareGPT schema that no longer
matches the data. This project's scripts follow the real file.

**Data quirks discovered so far:** roughly 30% of the images inside a
tarball have no annotation record ("orphans") -- the split script only
admits JSON-referenced images, so orphans cost disk but nothing else.

## Setup

Python 3.13 with CUDA-enabled PyTorch (see the install note inside
`requirements.txt` for fresh machines):

```bash
pip install -r requirements.txt
```

Each benchmark/training script directory carries its own standalone
`requirements.txt` pinned for that script's libraries (e.g. TRL/PEFT for
fine-tuning); install that file alone if you only want one variant.
Users manage their own environments -- the files just describe runnable
code.

Gated models (e.g. Gemma) additionally need license acceptance on the
Hugging Face website and an authenticated session:

```bash
hf auth login
```

## Workflow

Every step is idempotent -- re-running a command downloads nothing twice
and only extracts/splits/predicts what is missing.

| Step | Command | Notes |
|---|---|---|
| 1. Download | `python3 download_dataset.py --batches 1-5` | no flags = everything (~60 GB); `--only-annotations` = just the ~2.1 GB JSON |
| 2. Extract | `python3 extract.py --batches 1-2` | no flags = every downloaded tarball; markers make it resumable, `--force` re-extracts |
| 3. Split | `python3 make_splits.py` | 80/10/10, seed 42, over whatever is on disk; refuses to overwrite an existing split without `--force` |
| 4. Benchmark | `python3 benchmarks/gemma4_e2b/bench_gemma4_e2b_hf/bench_gemma4_e2b_hf.py` | test split only; resumable; `--limit N`; `--finetuned <dir> --run-name <name>` for adapters/fine-tuned models |
| 5. Evaluate | `python3 evaluate.py <results-dir>` | required path, no discovery; shared protocol: grapheme CER, WER, exact match, per-prefix breakdown |

## Design decisions

- **One library, one script.** Each inference/fine-tuning library gets its
  own script and requirements file under the model's directory, so users
  run whichever stack fits their resources; results are always plain JSONL
  with the same schema, so every variant scores through the same
  evaluation.
- **Split-first.** Benchmarks only ever score the `test` rows of
  `splits.csv`; there is no "score whatever is on disk" fallback, so
  numbers from different models are always comparable.
- **Predictions and scoring are separate.** Benchmark scripts emit
  per-sample predictions (JSONL: image path, ground truth, prediction,
  raw response, timing) and compute no metrics. One shared evaluation
  step will apply a single normalization protocol to every model.
  Storing raw predictions also means metrics can be recomputed without
  re-running any GPU time when the protocol evolves.
- **Reproducibility.** Exact dependency pins; seeded, materialized splits
  (regenerating after downloading more batches requires a deliberate
  `--force`, because it reshuffles assignments); every benchmark run
  writes a `run_info.json` recording model, prompt, library versions,
  and device.
- **Resumability.** Downloads resume; extractions skip completed batches
  via marker files; benchmark runs skip already-predicted samples.
- **Planned metrics** (per the protocol this project follows): CER at
  grapheme-cluster level (Unicode-aware, NFC-normalized -- conjuncts
  like `क्ष` count as one unit), codepoint CER, WER, and exact match,
  reported macro (per-sample) and micro (corpus-level), broken out by
  source/domain prefix.

## Hardware

Developed and benchmarked on a laptop with an 8 GB NVIDIA RTX 5050.
Models load with `device_map="auto"` (CPU offload if needed) and images
are processed one at a time. Full-test-split VLM runs are multi-hour
jobs on this class of hardware -- use `--limit` for pilots.
